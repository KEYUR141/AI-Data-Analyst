# AI Data Analyst

Current milestone: Django configuration, PostgreSQL wiring, CSV validation, private dataset storage, and session-scoped upload/preview/removal. Chat controls remain disabled until analysis is implemented.

New uploads also include a saved data profile: inferred column types, missing and distinct counts, numeric statistics, date ranges, and duplicate rows. See [profiling rules and flow](documents/data-profiling.md). Older uploads need re-uploading to generate a profile.

The browser workspace now accepts multiple CSV uploads and links to previews. Try `sample_data/sales.csv`. See [upload and persistence flow](documents/dataset-upload.md). A validation-only `POST /datasets/validate/` endpoint also accepts multipart `files` and returns per-file outcomes without saving them; see [validation policy](documents/csv-validation.md).

## Setup (PowerShell, repository root)

Activate your virtual environment, then:

```powershell
python -m pip install -r requirements-dev.txt
Copy-Item .env.example .env
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

Set SECRET_KEY in `.env` to the generated value, enclosed in quotes. Never commit `.env`. Set POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_HOST, and POSTGRES_PORT to your local database credentials. Missing required configuration explicitly prevents startup. Environment variables override `.env` values.

With Docker Desktop running, start the development database:

```powershell
docker compose up -d db
```

Alternatively create a PostgreSQL 14+ database and login role locally and update the POSTGRES_* variables. The example uses database `ai_data_analyst` and role `ai_analyst`. Passwords are used directly, without URL encoding; enclose values containing `#` in quotes. Django and Compose share the same database, user, and password variables. Example credentials are for local development only. Updating credentials does not change an existing database volume's credentials.

```powershell
python Project/manage.py check
python Project/manage.py migrate
python Project/manage.py runserver
```

Open http://127.0.0.1:8000/. Optional: `python Project/manage.py createsuperuser` for `/admin/`.

- `/health/` checks application liveness without a database query.
- `/ready/` checks database connectivity and returns 503 on failure; it does not check migration state.

## Verification

Optional Gemini credentials and generation settings are documented in [Gemini setup](documents/gemini-setup.md). Uploads do not require an LLM key. The dataset preview includes a structured planning form; see [analysis planning](documents/analysis-planning.md). Plans are validated and returned as JSON, without executing SQL.

```powershell
python Project/manage.py test app --settings=Project.test_settings
python Project/manage.py collectstatic --noinput
```

Tests use isolated settings: dataset integration tests use a temporary SQLite database and temporary files, while health tests mock database responses. They do not verify PostgreSQL. Normal settings require PostgreSQL with no SQLite fallback. Verify the actual database with migrations and `/ready/`. Run `python -m pytest -q` for the complete suite.

## Layout and scope

The existing `Project/Project` configuration and `Project/app` boilerplate are preserved. Templates are under `Project/templates`; local CSS is under `Project/static`. Feature apps will be added later. Tailwind compilation and HTMX interactions are deferred until interactive features. No CDN is needed for the base page.

Private uploads will live in ignored `var/uploads`, without public media routing. `staticfiles` is generated by collectstatic.

Compose currently provides only the development database. Full application Docker support, locked dependencies, architecture diagram, sample data, screenshots, and demo video are later milestones. Production needs strong secrets, production database credentials, allowed hosts/origins, and an appropriate HTTPS setup.
